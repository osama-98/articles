The SOLID Principles, Made Simple

Five guidelines that keep object-oriented code easy to change, test, and grow — each with a matching real-life analogy and a before/after PHP example.

S — Single Responsibility O — Open/Closed L — Liskov Substitution I — Interface Segregation D — Dependency Inversion

SOLID is a set of five object-oriented design principles, introduced by Robert C. Martin. The name is an acronym: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion.

They don't add features. They shape your code so a future change touches one small place instead of rippling everywhere — leaving software that is easier to maintain, test, and extend, with looser coupling between its parts. Treat them as guidelines, not strict laws.

S Single Responsibility

A class should have one job — and therefore only one reason to change.

The bakery: one worker who bakes, counts the stock, and rings up customers is overloaded — a change to any duty disrupts the others. Give each person a single, clear role instead.

Below, one Bakery class does all three jobs, so a change to billing risks breaking the baking. Split each duty into its own class.

Before
Bakery.php 
<?php

class Bakery
{
    public function bakeBread(): void
    {
        // mix, knead, bake
    }

    public function countStock(): void
    {
        // count flour, sugar, eggs
    }

    public function billCustomer(Order $order): void
    {
        // take payment, print receipt
    }
}
After
Bakery.php 
<?php

class Baker
{
    public function bakeBread(): Bread
    {
        // mix, knead, bake
    }
}

class InventoryManager
{
    public function countStock(): void
    {
        // count flour, sugar, eggs
    }
}

class Cashier
{
    public function bill(Order $order): void
    {
        // take payment, print receipt
    }
}

Why it helps: each class now changes for exactly one reason. Edits stay small and safe, every class is easy to test on its own, and each one can be reused elsewhere.

O Open / Closed

Open for extension, closed for modification — add new behavior without editing tested code.

The checkout: the till starts by taking credit cards, then needs PayPal. Rather than reopening the working card logic, you add PayPal as a new option beside it. The old code stays sealed and trusted.

Below, the processor grows a new if branch for every method — reopened and re-tested each time. Let each method implement a shared PaymentMethod interface instead.

Before
PaymentProcessor.php 
<?php

class PaymentProcessor
{
    public function pay(string $method, float $amount): void
    {
        if ($method === 'credit_card') {
            // charge the card
        } elseif ($method === 'paypal') {
            // call the PayPal API
        }
        // every new method forces an edit here
    }
}
After
PaymentProcessor.php 
<?php

interface PaymentMethod
{
    public function pay(float $amount): void;
}

class CreditCard implements PaymentMethod
{
    public function pay(float $amount): void
    {
        // charge the card
    }
}

class PayPal implements PaymentMethod
{
    public function pay(float $amount): void
    {
        // call the PayPal API
    }
}

class PaymentProcessor
{
    // add Apple Pay later as one new class — this never changes
    public function process(PaymentMethod $method, float $amount): void
    {
        $method->pay($amount);
    }
}

Why it helps: new requirements arrive as new classes, leaving tested code untouched. That lowers the risk of bugs and lets the system keep growing without turning fragile.

L Liskov Substitution

A subtype must work anywhere its parent is expected — with no surprises.

The birds: "every bird flies" sounds right until you meet a penguin. If your code expects any bird to fly, handing it a penguin breaks that expectation.

The principle (from Barbara Liskov): if S is a subtype of T, an S must be usable anywhere a T is. Below, Penguin inherits fly() only to throw. The fix: don't promise an ability a subtype can't keep — model "flying" separately.

Before
Birds.php 
<?php

class Bird
{
    public function fly(): void
    {
        // take off
    }
}

class Penguin extends Bird
{
    public function fly(): void
    {
        throw new Exception("Penguins can't fly!"); // breaks the promise
    }
}
After
Birds.php 
<?php

interface Bird
{
    public function eat(): void;
}

interface FlyingBird extends Bird
{
    public function fly(): void;
}

class Sparrow implements FlyingBird
{
    public function eat(): void {}
    public function fly(): void {}
}

class Penguin implements Bird
{
    public function eat(): void {} // just eats — never claims to fly
}

Why it helps: code that asks for a FlyingBird can never be handed something that can't fly. Substitution stays safe, behavior stays predictable, and polymorphism can be trusted.

I Interface Segregation

Don't force a class to depend on methods it never uses.

The office machine: a contract that says every device must print, scan, and fax forces a basic printer to pretend it can scan and fax. Offer smaller contracts so each device signs only what it does.

Below, one fat Machine interface drags scan() and fax() onto a printer that has neither. Split it into focused interfaces.

Before
Devices.php 
<?php

interface Machine
{
    public function print(Document $doc): void;
    public function scan(Document $doc): void;
    public function fax(Document $doc): void;
}

class SimplePrinter implements Machine
{
    public function print(Document $doc): void
    {
        // really prints
    }

    public function scan(Document $doc): void
    {
        throw new Exception('No scanner'); // forced, useless
    }

    public function fax(Document $doc): void
    {
        throw new Exception('No fax'); // forced, useless
    }
}
After
Devices.php 
<?php

interface Printer
{
    public function print(Document $doc): void;
}

interface Scanner
{
    public function scan(Document $doc): void;
}

class SimplePrinter implements Printer
{
    public function print(Document $doc): void {}
}

class OfficeMachine implements Printer, Scanner
{
    public function print(Document $doc): void {}
    public function scan(Document $doc): void {}
}

Why it helps: a class implements only what it truly does — no empty or throwing methods. Dependencies shrink, contracts stay clear, and a change to one role no longer ripples into classes that never used it.

D Dependency Inversion

Depend on abstractions, not on concrete details.

The wall switch: a light switch turns on whatever is wired to it — a lamp, a fan — without knowing the device. It depends on the idea of "something switchable," not on one specific appliance.

Below, the switch builds its own new Lamp(), so it can only ever control a lamp and can't be tested without one. Have it depend on a Switchable interface and receive the device from outside.

Before
Switch.php 
<?php

class PowerSwitch
{
    private Lamp $lamp;

    public function __construct()
    {
        $this->lamp = new Lamp(); // hard-wired to Lamp
    }

    public function press(): void
    {
        $this->lamp->turnOn();
    }
}
After
Switch.php 
<?php

interface Switchable
{
    public function turnOn(): void;
}

class Lamp implements Switchable
{
    public function turnOn(): void
    {
        // light up
    }
}

class Fan implements Switchable
{
    public function turnOn(): void
    {
        // start spinning
    }
}

class PowerSwitch
{
    // any Switchable works — lamp, fan, or a fake in tests
    public function __construct(private Switchable $device) {}

    public function press(): void
    {
        $this->device->turnOn();
    }
}

Why it helps: swap the device (or mock it in a test) without touching PowerSwitch at all. The high-level logic stays decoupled from the details — which is exactly what dependency injection makes easy.

In Short

Single Responsibility · Open/Closed · Liskov Substitution · Interface Segregation · Dependency Inversion.

Each one pushes toward the same goal: small, focused pieces that depend on stable abstractions, so change stays local and testing stays easy.

They are guidelines, not commandments — apply them where they reduce pain, and don't over-engineer simple code just to satisfy an acronym.
