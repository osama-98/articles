مبادئ SOLID بالتبسيط

خمسة مبادئ تجعل كودك الـObject-Oriented أسهل في التعديل والاختبار والتوسّع — كل مبدأ بمثال من الواقع يطابق مثال PHP «قبل وبعد».

S — Single Responsibility O — Open-Closed L — Liskov Substitution I — Interface Segregation D — Dependency Inversion

في هندسة البرمجيات، تُعدّ الـSOLID واحدة من أكثر مجموعات مبادئ التصميم شيوعًا في تطوير برامج الـObject-Oriented Programming. قدّم Robert C. Martin هذه المبادئ في ورقته البحثية عام 2000 بعنوان “Design Principles and Design Patterns”، ثم بُنِيت هذه المفاهيم لاحقًا على يد Michael Feathers الذي قدّم اختصار SOLID. والاسم اختصار للمبادئ الخمسة: Single Responsibility وOpen-Closed وLiskov Substitution وInterface Segregation وDependency Inversion.

هي لا تضيف مزايا جديدة، بل تنظّم الكود بحيث يبقى أي تعديل مستقبلي محصورًا في مكان صغير بدل أن ينتشر في كل مكان. والنتيجة كود أسهل في الصيانة والاختبار والتوسّع، وأقل ترابطًا (coupling) بين أجزائه، ويتجنّب الـcode smell وكثرة الـrefactoring. تعامل معها كإرشادات لا كقواعد صارمة.

S مبدأ الـ Single Responsibility

يجب أن يكون للـclass سبب واحد فقط للتغيير.

مثال من الواقع — المخبز: العامل الذي يخبز ويتابع المخزون ويحاسب الزبائن في آنٍ واحد مُثقَل بالأعباء، وأي تغيير في إحدى مهامه يربك الباقي. الأفضل أن يكون لكل شخص دور واحد واضح.

في المثال أدناه، الـBakery class واحد يؤدي المهام الثلاث، فأي تغيير في المحاسبة قد يكسر الخَبز. لذلك نفصل كل مسؤولية في class مستقل.

قبل
Bakery.php 
<?php

class Bakery
{
    public function bakeBread(): void
    {
        // mix, knead, bake
    }

    public function countStock(): void
    {
        // count flour, sugar, eggs
    }

    public function billCustomer(Order $order): void
    {
        // take payment, print receipt
    }
}
بعد
Bakery.php 
<?php

class Baker
{
    public function bakeBread(): Bread
    {
        // mix, knead, bake
    }
}

class InventoryManager
{
    public function countStock(): void
    {
        // count flour, sugar, eggs
    }
}

class Cashier
{
    public function bill(Order $order): void
    {
        // take payment, print receipt
    }
}

لماذا يفيد؟ الـclass الذي له مسؤولية واحدة يتغيّر لسبب واحد فقط، فتبقى التعديلات صغيرة وآمنة، وله test cases أقل واعتمادية (dependencies) أقل عليه، ويسهل تنظيمه وإعادة استخدامه.

O مبدأ الـ Open-Closed

يجب أن تكون الـEntities مفتوحة للإضافة ولكن مغلقة للتعديل.

مثال من الواقع — الدفع: صندوق الدفع يبدأ بالبطاقات الائتمانية، ثم يحتاج إلى PayPal. بدل فتح الكود العامل والمخاطرة بكسره، تضيف PayPal كخيار جديد بجانبه، فيبقى القديم مغلقًا وموثوقًا.

في المثال أدناه، الـprocessor يضيف شرط if جديدًا مع كل وسيلة دفع، فيُعاد فتحه واختباره في كل مرة. الأفضل أن تنفّذ كل وسيلة دفع الـPaymentMethod interface المشترك.

قبل
PaymentProcessor.php 
<?php

class PaymentProcessor
{
    public function pay(string $method, float $amount): void
    {
        if ($method === 'credit_card') {
            // charge the card
        } elseif ($method === 'paypal') {
            // call the PayPal API
        }
        // every new method forces an edit here
    }
}
بعد
PaymentProcessor.php 
<?php

interface PaymentMethod
{
    public function pay(float $amount): void;
}

class CreditCard implements PaymentMethod
{
    public function pay(float $amount): void
    {
        // charge the card
    }
}

class PayPal implements PaymentMethod
{
    public function pay(float $amount): void
    {
        // call the PayPal API
    }
}

class PaymentProcessor
{
    // add Apple Pay later as one new class — this never changes
    public function process(PaymentMethod $method, float $amount): void
    {
        $method->pay($amount);
    }
}

لماذا يفيد؟ يهدف المبدأ إلى توسيع الـbehavior دون تغيير الموجود لتجنّب الأخطاء؛ فوسائل الدفع الجديدة تأتي كـclasses جديدة دون مساس بالكود العامل، فيستمر النظام في النمو دون أن يصبح هشًّا.

L مبدأ الـ Liskov Substitution

يجب أن يكون كل subclass قابلًا للاستبدال بالـbase class دون أن يَكسر ذلك البرنامج.

مثال من الواقع — الطيور: «كل طائر يطير» تبدو صحيحة حتى تقابل بطريقًا. فإذا كان كودك يتوقّع أن يطير أي طائر، فإن تمرير بطريق إليه يكسر هذا التوقّع.

المبدأ — من Barbara Liskov — ينص على أنه إذا كان S نوعًا فرعيًا من T فيجب أن يصلح استخدام S في أي مكان يُتوقَّع فيه T. وفي المثال أدناه يرث Penguin الـmethod fly() ثم يرمي خطأ. الحل ألّا تَعِد بقدرة لا يقدر عليها النوع الفرعي، بل تفصل «الطيران» في interface مستقلة.

قبل
Birds.php 
<?php

class Bird
{
    public function fly(): void
    {
        // take off
    }
}

class Penguin extends Bird
{
    public function fly(): void
    {
        throw new Exception("Penguins can't fly!"); // breaks the promise
    }
}
بعد
Birds.php 
<?php

interface Bird
{
    public function eat(): void;
}

interface FlyingBird extends Bird
{
    public function fly(): void;
}

class Sparrow implements FlyingBird
{
    public function eat(): void {}
    public function fly(): void {}
}

class Penguin implements Bird
{
    public function eat(): void {} // just eats — never claims to fly
}

لماذا يفيد؟ يهدف المبدأ إلى فرض الـConsistency، فالكود الذي يطلب FlyingBird لن يُمرَّر إليه أبدًا ما لا يطير، ويمكن استخدام الـparent والـchild بنفس الطريقة دون أخطاء.

I مبدأ الـ Interface Segregation

لا ينبغي أبدًا إجبار العميل على تنفيذ interface لا يستخدمها.

مثال من الواقع — آلة المكتب: عقد يفرض على كل جهاز أن يطبع ويمسح ضوئيًا ويرسل فاكسًا يُجبر الطابعة البسيطة على التظاهر بقدرات لا تملكها. الأفضل تقديم عقود أصغر يوقّع كل جهاز منها ما يؤديه فقط.

في المثال أدناه، الـMachine interface الضخم يفرض scan() وfax() على طابعة لا تملك أيًّا منهما. لذلك نقسّمه إلى interfaces متخصّصة.

قبل
Devices.php 
<?php

interface Machine
{
    public function print(Document $doc): void;
    public function scan(Document $doc): void;
    public function fax(Document $doc): void;
}

class SimplePrinter implements Machine
{
    public function print(Document $doc): void
    {
        // really prints
    }

    public function scan(Document $doc): void
    {
        throw new Exception('No scanner'); // forced, useless
    }

    public function fax(Document $doc): void
    {
        throw new Exception('No fax'); // forced, useless
    }
}
بعد
Devices.php 
<?php

interface Printer
{
    public function print(Document $doc): void;
}

interface Scanner
{
    public function scan(Document $doc): void;
}

class SimplePrinter implements Printer
{
    public function print(Document $doc): void {}
}

class OfficeMachine implements Printer, Scanner
{
    public function print(Document $doc): void {}
    public function scan(Document $doc): void {}
}

لماذا يفيد؟ يهدف المبدأ إلى تقسيم مجموعة الـactions إلى مجموعات أصغر، فينفّذ كل class الـactions المطلوبة منه فقط دون زيادات، فتقلّ الاعتمادية وتبقى العقود واضحة.

D مبدأ الـ Dependency Inversion

الـHigh-level module يجب ألا تعتمد على الـLow-level module مباشرة؛ كلاهما يعتمد على Abstractions.

مثال من الواقع — مفتاح الكهرباء: المفتاح يشغّل ما يُوصَّل به — مصباحًا أو مروحة — دون أن يعرف نوع الجهاز. هو يعتمد على فكرة «شيء قابل للتشغيل» لا على جهاز بعينه.

في المثال أدناه يُنشئ المفتاح الـobject بنفسه عبر new Lamp()، فلا يقدر إلا على التحكّم بمصباح ولا يمكن اختباره بدونه. الأفضل أن يعتمد على الـSwitchable interface وأن يُمرَّر إليه الجهاز من الخارج.

قبل
Switch.php 
<?php

class PowerSwitch
{
    private Lamp $lamp;

    public function __construct()
    {
        $this->lamp = new Lamp(); // hard-wired to Lamp
    }

    public function press(): void
    {
        $this->lamp->turnOn();
    }
}
بعد
Switch.php 
<?php

interface Switchable
{
    public function turnOn(): void;
}

class Lamp implements Switchable
{
    public function turnOn(): void
    {
        // light up
    }
}

class Fan implements Switchable
{
    public function turnOn(): void
    {
        // start spinning
    }
}

class PowerSwitch
{
    // any Switchable works — lamp, fan, or a fake in tests
    public function __construct(private Switchable $device) {}

    public function press(): void
    {
        $this->device->turnOn();
    }
}

لماذا يفيد؟ بهذا الفصل (Decoupling) يمكنك تبديل الجهاز أو استبداله بنسخة وهمية للاختبار دون أن تلمس PowerSwitch إطلاقًا، لأنه يعتمد على الـinterface لا على الأداة — وهذا ما يسهّله الـdependency injection.

باختصار

S Single Responsibility · O Open-Closed · L Liskov Substitution · I Interface Segregation · D Dependency Inversion.

كلها تصبّ في هدف واحد: قطع صغيرة ومتخصّصة تعتمد على abstractions مستقرة، فيبقى التغيير محصورًا والاختبار سهلًا.

وتذكّر أنها إرشادات لا أوامر؛ طبّقها حيث تخفّف الألم، ولا تُبالغ في هندسة كود بسيط لمجرد إرضاء اختصار.
